## Detailed Findings & Remediation Plan

### FINDING-001: Hardcoded Default Admin Seed Credential in Schema
- **Severity**: CRITICAL
- **Antislop Rules**: R-36 (No Fabricated Claims), C-2 (Functional Completeness & Integrity)
- **Status**: RESOLVED
- **Evidence**: `schema.sql:157-159`
  ```sql
  -- [REDACTED: Hardcoded default admin credential seed with static password hash and demo salt]
  INSERT OR IGNORE INTO users (id, email, password_hash, role) VALUES 
  ('usr_admin', '[REDACTED_DEFAULT_ADMIN_EMAIL]', '[REDACTED_LEGACY_SHA256_HASH_AND_SALT]', 'admin');
  ```
- **Impact**: Any deployment initializing the schema previously created a known administrative backdoor with default pre-seeded credentials.
- **Remediation**: Removed default admin seed insert from `schema.sql`. Admin users must be explicitly provisioned via secure initial setup script or environment-driven migration without default passwords. Verified in schema.

### FINDING-002: Fail-Open Payment Gateway Webhooks & Missing Signature Enforcements
- **Severity**: CRITICAL
- **Antislop Rules**: C-2, C-5 (Evidence Over Claims)
- **Status**: RESOLVED
- **Evidence**:
  - `src/services/payments.ts:78`: `if (this.serverKey && signatureKey)` skips signature check if `signature_key` is omitted in payload.
  - `src/services/payments.ts:159`: `if (this.webhookToken && callbackToken !== this.webhookToken)` skips token verification if webhookToken is unconfigured.
  - `src/services/payments.ts:238`: `if (this.webhookSecret)` skips Svix HMAC verification if secret is unconfigured.
- **Impact**: Unauthenticated callers can forge webhook calls to `/api/webhooks/midtrans`, `/xendit`, or `/sumopod` and mark unpaid orders as `paid`, triggering automatic product dispatch.
- **Remediation**: Webhook verification strictly fails closed. Requires valid signatures/tokens; throws authentication error if signature header/token is missing or fails verification.

### FINDING-003: Unauthenticated HeroSMS Webhook Endpoint
- **Severity**: CRITICAL
- **Antislop Rules**: C-2
- **Status**: RESOLVED
- **Evidence**: `src/api/webhooks.ts:150-170`
- **Impact**: Any unauthenticated public client can send a POST request with arbitrary `activation_id` and OTP code/text, corrupting SMS activation records and spoofing verification codes.
- **Remediation**: Authenticated HeroSMS webhook via secret verification token header (`x-webhook-secret`) using constant-time comparison. Rejects unauthorized calls with 401 Unauthorized, without accepting or logging secrets in query parameters.

### FINDING-004: Credit Topup Double-Crediting Race Condition & Non-Atomic Ledger
- **Severity**: CRITICAL
- **Antislop Rules**: C-2, C-4 (Resilience)
- **Status**: RESOLVED
- **Evidence**: `src/api/webhooks.ts:83-125`, `src/services/credits.ts:20-85`
- **Impact**: When multiple webhook retries or concurrent events arrive for the same topup order, the lack of atomic synchronization allows duplicate credits. In `src/services/credits.ts`, balance update and transaction logging in `debitCredit` were previously executed in separate round-trips without D1 `batch()`, risking ledger divergence if one query failed, and lacking retry idempotency for duplicate `reference_id`s.
- **Remediation**:
  1. Implemented D1-safe atomic batch execution in `debitCredit` (`db.batch([balanceStmt, txnStmt])`) tying the balance decrement and ledger row insertion into a single transaction.
  2. Guarded ledger insertion with `WHERE (SELECT changes()) > 0` so no ledger row is written when balance is insufficient (`balance < amount`), and strictly inspected batch result metadata (`balanceChanges > 0 && txnChanges > 0`) rather than assuming success.
  3. Added idempotent retry protection for `debitCredit`: returns the existing debit record without re-decrementing balance if `reference_id` was already debited, backed by unique partial index `idx_credit_txn_debit_ref` (`WHERE type = 'debit' AND reference_id IS NOT NULL`) for concurrency safety and automatic rollback.
  4. Implemented an atomic state transition claim on pending topup transactions (`UPDATE ... WHERE reference_id = ? AND type = 'topup_pending'`) and verified affected-row count (`meta.changes > 0`) before crediting the user balance in `addCredit` / webhooks, guaranteeing idempotency under concurrent retries.

### FINDING-005: Insecure Password Hashing & Timing-Attack Vulnerable Comparison
- **Severity**: HIGH
- **Antislop Rules**: C-2
- **Status**: RESOLVED
- **Evidence**: `src/services/auth.ts:5-20`
  ```typescript
  const hashBuffer = await crypto.subtle.digest('SHA-256', data);
  ...
  return computed === storedHash;
  ```
- **Impact**: Single-iteration SHA-256 is vulnerable to high-speed offline dictionary and rainbow table cracking. String equality `===` leaks execution time, exposing password hashes to timing attacks.
- **Remediation**:
  1. Implement PBKDF2 using WebCrypto (`crypto.subtle.importKey`, `crypto.subtle.deriveBits`, HMAC-SHA256, 100,000 iterations, 16+ bytes cryptographically secure random salt).
  2. Use versioned hash format: `pbkdf2:v1:100000:<salt_hex>:<hash_hex>`.
  3. Implement constant-time comparison buffer comparison (`crypto.subtle.timingSafeEqual`).
  4. Preserve backward compatibility by verifying legacy single SHA-256 hashes with constant-time equality.

### FINDING-006: Google OAuth Missing State/PKCE & Unverified Email Account Takeover Risk
- **Severity**: HIGH
- **Antislop Rules**: C-2
- **Status**: RESOLVED
- **Evidence**: `src/api/auth.ts:106-161`
- **Impact**: OAuth authorization redirect generates no `state` parameter or PKCE `code_challenge`, exposing authentication flow to OAuth CSRF and authorization code interception. Furthermore, Google user profile does not verify `email_verified`, permitting malicious accounts with spoofed unverified emails to claim existing user accounts.
- **Remediation**:
  1. Generate random `state` and PKCE `code_verifier` / `code_challenge` stored in secure, HttpOnly, SameSite cookies.
  2. Verify `state` in `/callback` against the cookie, and pass `code_verifier` during token exchange.
  3. Verify `userInfo.email_verified === true` before user lookup or creation.

### FINDING-007: Concurrent Stock Oversell & Permanently Stuck Order Item Fulfilment
- **Severity**: HIGH
- **Antislop Rules**: C-2, C-4
- **Status**: RESOLVED
- **Evidence**: `src/services/fulfilment.ts:31-37,62-84`
- **Impact**:
  1. Stock allocation assigns codes without verifying whether `UPDATE stock_codes ... WHERE is_used = 0` updated > 0 rows, allowing race conditions where two simultaneous orders allocate the exact same stock code to different users.
  2. If an exception is thrown during fulfilment, items remain stuck in `'processing'` status permanently and cannot be resumed or refunded.
- **Remediation**:
  1. Check affected row changes on stock code assignment; if zero, re-query or abort allocation cleanly.
  2. Wrap fulfilment loop in structured try/catch to transition failed items to `'failed'` with error detail, preventing stuck states.

### FINDING-008: Simulated-Pay Endpoint Missing Ownership Verification
- **Severity**: HIGH
- **Antislop Rules**: C-2
- **Status**: RESOLVED
- **Evidence**: `src/api/orders.ts:366-387`
- **Impact**: Any authenticated user can call `/api/orders/:id/simulated-pay` on an order ID belonging to any other user, bypassing payment and forcing fulfillment.
- **Remediation**: Enforce `order.user_id === user.id || user.role === 'admin'`. Ensure strict gate `c.env.APP_ENV === 'development' && c.env.ALLOW_SIMULATED_PAYMENTS === 'true'`.

### FINDING-010: Inaccessible Dialogs/Drawers Lacking ARIA, Escape Handling & Focus Traps
- **Severity**: HIGH
- **Antislop Rules**: R-26, R-32, antislop-human
- **Status**: RESOLVED
- **Evidence**: `src/components/ProductDetailModal.tsx:31-39`, `src/components/AuthModal.tsx:33-41`, `src/components/CartDrawer.tsx:107-124`
- **Impact**: Modal dialogs and cart drawer lack `role="dialog"`, `aria-modal="true"`, `aria-labelledby`, keyboard `Escape` dismissal, focus capture, and labeled close buttons, causing screen reader failure and keyboard navigation traps.
- **Remediation**: Added standard dialog attributes (`role="dialog"`, `aria-modal="true"`, `aria-labelledby`, `tabindex="-1"`), implemented lightweight zero-dependency focus-trap hook (`src/hooks/useFocusTrap.ts`) for `AuthModal`, `ProductDetailModal`, and `CartDrawer`. On dialog open, captures the previously focused element and moves focus to the close button (`aria-label` matching `"Tutup..."`) or first focusable control. Traps keyboard Tab and Shift+Tab cycling within the dialog, restores focus to trigger element on close/unmount, and preserves Escape dismissal and aria labeling. Verified with dedicated test suite `tests/focustrap.test.ts`.
