# Sumopod credit system with auto-refund

This change adds a complete credit/topup system backed by the Sumopod QRIS payment gateway. Users top up credits via Sumopod, spend them on digital products and OTP numbers at checkout, and receive automatic refunds when fulfilment fails. The backend adds a credit service (balance, debit, refund), a credits API, a Svix-verified Sumopod webhook, and credit-pay support in the orders checkout flow. The frontend adds a TopupPage with presets and history, success/cancel landing pages, a credit balance badge in the Navbar, and a credit payment option in the CartPage.

**Watch for:** Race condition in the debit path where balance is checked then decremented in two separate queries — concurrent requests can overdraw the account (confirmed). The topup webhook credits the user but also inserts a second "pending" tracking row that it then deletes, creating a window where the balance is double-counted if the webhook fires twice before the DELETE executes (likely). The `REAL` column type for monetary balance invites floating-point rounding errors on high-frequency operations (confirmed).

## High-level view

The credit service implements balance operations (topup, debit, refund) as separate read-then-write steps against D1. Because D1 does not support row-level locks or multi-statement transactions within a single `.run()` call, the check-then-decrement pattern in `debitCredit` opens a time-of-check/time-of-use window that allows double-spending under concurrent webhook or checkout pressure.

The Sumopod gateway adapter follows the existing PaymentGateway interface pattern with sandbox/production URL switching and Svix HMAC-SHA256 webhook verification. However, the signature is computed over `JSON.stringify(payload)` (a re-serialized parsed body) rather than the raw request bytes — if the original body has different whitespace or key ordering, verification will fail in production.

The webhook handler for topup completion inserts a new credit transaction via `addCredit` and then deletes the "pending" tracking row. This two-step approach means a retried webhook that arrives before the DELETE completes will find the pending row again and credit the user a second time.

The monetary columns use `REAL` (IEEE 754 double), which will silently accumulate rounding errors on IDR values that don't fit binary representation. Auto-refund in fulfilment guards against double-refund by checking for an existing refund transaction before issuing a new one, but partial failures leave the order in "paid" status with no indication to the user that some items were refunded.

<details>
<summary>Issues (7)</summary>

1. **Debit race condition** — `debitCredit` does SELECT then UPDATE in two queries; concurrent requests can overdraw the balance. Use `UPDATE ... WHERE balance >= amount` as a single atomic check-and-decrement.
2. **Topup webhook double-credit** — The webhook finds the pending row, calls `addCredit`, then deletes the pending row. A retried webhook arriving before the DELETE will credit again. Add an idempotency check (e.g., check whether a completed topup transaction for this reference already exists before crediting).
3. **REAL column for money** — `user_credits.balance` and `credit_transactions.amount` use `REAL`, which cannot represent all IDR integers exactly. Use `INTEGER` (storing the value in the smallest unit, or just IDR since the minimum is 10,000 and all operations are whole-number).
4. **Svix signature computed over re-serialized JSON** — `verifyWebhook` receives a parsed object and re-serializes it with `JSON.stringify`. The HMAC must be computed over the raw request body bytes to match Sumopod's signature. Pass the raw body string into the verification method.
5. **Missing auth on topup routes** — The topup pages (`/topup`, `/topup/success`, `/topup/cancel`) are not wrapped in a route guard; the component-level redirect only fires after React hydration, briefly exposing the page content to unauthenticated users and allowing the balance API to fire unauthenticated.
6. **No maximum topup cap** — The `/topup` endpoint enforces a minimum (10,000 IDR) but no maximum, allowing arbitrarily large payments to be created via the API.
7. **Pending topup appears as completed in history** — The pending topup transaction is inserted with `type = 'topup'` immediately, making it appear in the user's history as a completed topup before payment finishes. No cleanup for abandoned/expired topups.

## Debit atomicity gap

The `debitCredit` function in `src/services/credits.ts` reads the balance, compares it to the requested amount in application code, and then issues a separate UPDATE to subtract:

```typescript
const currentBalance = await getBalance(db, userId);
if (currentBalance < amount) {
  return { success: false, error: 'Insufficient credit balance' };
}
// ... separate UPDATE:
await db.prepare(`UPDATE user_credits SET balance = balance - ? ...`).bind(amount, userId).run();
```

Two concurrent checkout requests for the same user can both pass the balance check before either decrements, resulting in a negative balance. D1 supports conditional UPDATEs: `UPDATE user_credits SET balance = balance - ? WHERE user_id = ? AND balance >= ?` would return zero `meta.changes` when the balance is insufficient, collapsing the check and mutation into a single atomic statement.

## Topup webhook idempotency

In `src/api/webhooks.ts`, the Sumopod handler for topup payments finds the pending transaction, credits the user, then deletes the pending record:

```typescript
const topupTxn = await c.env.DB.prepare(
  "SELECT * FROM credit_transactions WHERE reference_id = ? AND type = 'topup' LIMIT 1"
).bind(orderId).first<any>();

if (topupTxn) {
  await addCredit(c.env.DB, topupTxn.user_id, topupTxn.amount, 'topup', orderId, ...);
  await c.env.DB.prepare('DELETE FROM credit_transactions WHERE id = ?').bind(topupTxn.id).run();
}
```

If Sumopod retries the webhook (their docs state they retry on non-2xx), and the retry arrives before the DELETE runs — or if the first request fails after `addCredit` but before the DELETE — the pending row still exists and the handler credits again. A safer approach: before calling `addCredit`, check whether a completed topup transaction with this `reference_id` already exists.

## Money stored as REAL

The migration defines `balance REAL NOT NULL DEFAULT 0` and `amount REAL NOT NULL`. In SQLite's REAL affinity, `0.1 + 0.2 != 0.3`. Sumopod's webhook payload includes `net_amount` (amount minus fee) which could be non-integer. If the net amount is ever used for crediting, or if the system extends to non-IDR currencies, floating-point accumulation will produce visible balance discrepancies. Switching to INTEGER (whole IDR) eliminates this class of bug entirely since all current operations use round thousands.

## Signature verification over re-serialized body

The Svix verification in `SumopodGateway.verifyWebhook` computes the HMAC over `JSON.stringify(payload)`:

```typescript
const signedContent = `${svixId}.${svixTimestamp}.${JSON.stringify(payload)}`;
```

The `payload` argument is already parsed from `await c.req.json()`. JSON parsing discards original formatting — whitespace, key order, and escape sequences are normalized. Sumopod's server computes the HMAC over the raw HTTP body bytes. If the raw body was `{"event_type":"payment.completed", "data":{...}}` (with a space after the colon in one spot), `JSON.stringify` won't reproduce that exact string, and the signature check will fail.

The fix is to pass the raw body string into verification: call `await c.req.text()` to get the raw bytes, then `JSON.parse` separately for field extraction, and use the raw string for HMAC computation.

## Pending topup pollutes history

The `/topup` endpoint inserts a `credit_transactions` row with `type = 'topup'` immediately, before the user has actually paid. The `/history` endpoint returns all transactions including this pending one, displaying it with a positive amount as if the topup succeeded. If payment is never completed (user abandons, payment expires), the stale row remains indefinitely. Consider using a separate `status` field or a different type (e.g., `'topup_pending'`) that the history endpoint can filter out.

## Partial fulfilment leaves ambiguous order status

If fulfilment partially succeeds (some items fulfilled, some failed), the user gets refunded only for the failed items. The order remains in "paid" status with a mix of fulfilled and failed items — there's no partial-refund status on the order itself. A user viewing their order history sees "paid" but has received refund credits back for some items, with no visible explanation on the order detail page.
